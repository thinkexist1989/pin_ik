# 阶段 D 实施草案

日期：2026-11-06。基线：`c8592c5`。

状态：用户已确认先实施 D1 工作线程配置与验证工具，保持同步双求解器；目标控制器是另一台机器。本机进行接口和工具验证，目标控制器的参数选择及实时验收留待部署测试。

## 已有依据

[阶段 C 报告](REALTIME_IK_STAGE_C_VALIDATION.md)记录了工作线程晚开始的超期样本。一个 C 样本总耗时 1462 µs，其中 NLopt 工作线程在发布后 1438 µs 才开始执行，随后仅消耗约 1.65 µs CPU。发布至开始的间隔含通知、锁交接及调度，现有探针不能进一步区分各自占比。

当前库已有两个常驻线程和每轮完成屏障，但没有公开的工作线程亲和性或调度配置接口。不能跳过完成屏障来缩短返回时间，否则上一请求可能继续访问后续请求的状态。

本机检查结果：i7-1260P、16 个逻辑 CPU、12 个物理 core 编号，内核 `6.8.1-1061-realtime`；检查进程为 `SCHED_OTHER`，允许 CPU 0–15。CPU 0/1、2/3、4/5、6/7 分别共享 core，其余 CPU 的 core 编号不同。实时优先级资源上限为 99，内存锁定上限为 100 MiB。这些是当前检查进程的信息，不代表实际控制器线程配置，也不等于实时调度设置已成功执行。

## 已确认的 D1：显式线程配置

保持同步双求解器、求解模式和结果语义，增加非实时初始化/空闲阶段的配置能力：

- 控制器分别指定 Newton、NLopt 工作线程的 CPU 集合、调度策略和优先级；不在通用库内选定 CPU 编号或优先级。
- 提供实际生效配置的查询，基准记录调用线程及两个工作线程的实际值。
- 参数无效、权限不足或设置失败时返回明确错误；不能把未生效的实时配置记录为成功。采用单线程、单属性的显式操作，不提供隐式多项事务；前一步成功后的状态保持生效，后一步失败时由调用端决定恢复或终止初始化。
- `CartToJnt()` 路径不设置亲和性、不调整优先级、不创建线程；配置操作不与求解并发，遵循现有实例使用约束。
- 调用线程配置、进程内存锁定、预触页和系统级隔离由控制器或独立基准显式管理。非 Linux 平台应明确报告不支持，不影响未使用该功能的原有调用。

公开接口为 `setWorkerThreadAffinity`、`setWorkerThreadScheduling`、`getWorkerThreadSettings`，均限非实时空闲阶段。参数错误抛出 `std::invalid_argument`，系统操作失败抛出含原始错误码的 `std::system_error`。亲和性可能被系统约束缩减，调用端必须读回；基准工具对读回不一致的请求拒绝测量。单求解器、延迟启动 NLopt 和异步求解未纳入本次范围。

## 集成端待核实问题

只读检查相邻 `rocos-app` 仓库发现：`src/model.cpp` 中 `ParseUrdf`、`UpdateSolvers`、`SetPosLimits` 和 `CloneForPreview` 创建 `PIN_IK` 时均省略预算参数，使用库默认 5 ms。尚未确认该源码是否对应用户实际控制器。

若确认它是本次集成端，需要同时处理：

1. 伺服实例显式传入实际 IK 预算；550 µs 目前只是基准参数，不直接作为生产配置。
2. 求解器重建后重新应用已确认的工作线程配置。
3. 预览实例与伺服实例区分配置，避免把后台预览也赋予伺服线程的资源。

本次未修改 `rocos-app`，也未启动控制器或机器人。集成端代码仅作为后续部署核查线索。

## 验证方案

功能检查覆盖配置读回、两个工作线程的独立配置、错误参数与设置失败、配置后连续求解、线程 ID 保持不变、空闲更新及析构。权限不允许的实验应记录为未执行，不计为通过。

同一模型、输入、seed 策略、模式、精度、预算下，逐项比较：

| 组别 | 唯一新增因素 |
| --- | --- |
| C 基线 | 原调度和亲和性 |
| D1-A | 仅改变亲和性 |
| D1-B | 仅改变调度策略/优先级 |
| D1-C | 组合配置 |

CPU 编号、优先级和预算由确认后的验证环境决定。测量同时覆盖连续调用及绝对时刻 1 kHz 释放；重复并倒序运行，单独比较背景负载。继续记录成功率、FK/限位、P99/P99.9/最大耗时、超预算和释放超期；分段插桩与正式生产库计时分开。

真实控制器验收仍按原方案执行至少 1,000,000 周期，包含其他控制工作；本机独立基准不替代整机验收。

# PIN-IK 1000 Hz 逆运动学优化方案

日期：2026-11-06

状态：阶段 A、B 已实现并通过本地正确性验证，C、D 尚未实施

代码基线：`553fd1f`

阶段 A 的代码变更、KDL TRAC-IK 对比、平均和最大耗时及 1 kHz 测试边界见 [阶段 A 验证报告](REALTIME_IK_STAGE_A_VALIDATION.md)。整机 1 ms 零超期验收仍待后续完成。

阶段 B 的截止时间、取消修复、工作区复用及三方正确性和性能对比见 [阶段 B 验证报告](REALTIME_IK_STAGE_B_VALIDATION.md)。阶段 B 功能正确性通过，短预算周期测试仍有失败和超期，不能据此宣称硬实时目标已达成。

目标是消除每个伺服周期中创建和回收线程的开销，并降低 `CartToJnt()` 的计算耗时和尾部时延。建议先实现每个 `PIN_IK` 实例独占的两个常驻工作线程，再按测量结果优化停止响应、临时内存和重复运动学计算。

**常驻线程可以消除本库逐次创建线程的开销，但不能单独保证每次调用在 1 ms 内返回。** 同步接口仍须等待两个求解器结束本轮任务；调度延迟、迭代耗时和取消响应都必须计入预算。本文将线程生命周期验收与控制器整周期验收分别定义。

## 1 当前实现及性能影响

本节记录 `553fd1f` 优化前基线。阶段 A、B 的实际变更与验证结果分别见对应报告；本表不表示优化后仍存在全部问题。

| 位置 | 当前行为 | 对本次优化的影响 |
| --- | --- | --- |
| [pin_ik.cpp](../src/pin_ik.cpp) 的 `CartToJnt()` | 每次创建两个 `std::thread`，随后逐一 `join()` | 每周期包含线程创建、调度和资源回收开销 |
| [pin_ik.hpp](../include/pin_ik/pin_ik.hpp) 的构造函数默认参数 | `maxtime = 0.005`，即 5 ms | 不能直接用默认预算满足 1 ms 伺服周期 |
| `runSolver()` | 在共享时间预算内反复求解、随机重启；`Speed` 获得解后停止 | 一次 `CartToJnt()` 内可能执行多轮底层求解 |
| `runSolver()` 的结果临界区 | 持有 `mtx_` 时去重、扩容、评分；`Manip*` 还计算雅可比和 SVD | 增加锁占用时间；两个工作线程会争用 |
| [pinocchio_tl.cpp](../src/pinocchio_tl.cpp) | 迭代内构造动态雅可比、临时向量和分解对象 | 存在重复分配与初始化成本 |
| [pinocchio_types.hpp](../include/pin_ik/pinocchio_types.hpp) 的配置转换 | 每次返回新建的 `Eigen::VectorXd` | Newton 每轮的 FK 和雅可比调用分别执行转换 |

| 三个求解相关类的 `fRand()` | 使用进程级 `rand()` 状态 | 随机序列受线程交错影响；实现可能有共享状态同步开销 |
| 两个底层求解器的 `abort()` | 设置原子标志，由迭代或回调检查 | 是协作式停止，不能立即中断当前计算 |
| `setLimits()` | 调用 `initialize()`，重建两个底层求解器 | 常驻线程不能永久保存旧求解器引用 |
| [standalone_tests.cpp](../tests/standalone_tests.cpp) | 超时测试仅要求不可达求解在 1 秒内退出 | 现有测试不足以验证 1000 Hz 稳定性 |

当前 `Speed` 的精确行为也需要保留：任一线程记录解后触发尽快结束，但两个线程可能都提交候选解，最终仍按 `JointErr` 排序选择。本轮线程改造不将它静默改成“只保留第一个解”。`Distance` 和 `Manip*` 则继续在预算内搜索并选择最优候选。

## 3 常驻线程与单任务槽

每个实例固定拥有一个 Newton 工作线程和一个 NLopt 工作线程。构造时启动，空闲时等待，析构时唤醒退出并 `join()`。不用通用线程池和任务队列：现有接口一次只接受一个同步求解请求，积压的旧目标不适合逐周期控制。

建议新增以下私有状态，名称可在实现时调整：

| 状态 | 用途及同步方式 |
| --- | --- |
| `worker_mutex` | 保护任务发布、序号、就绪数、完成数、退出状态和异常槽 |
| `work_cv` | 通知两个工作线程有新任务或需要退出 |
| `state_cv` | 通知构造函数两个线程已经就绪，或通知调用线程本轮完成 |
| `generation` | 递增任务序号；每个工作线程维护自己的 `seen_generation` |
| `ready_workers`、`completed_workers` | 分别用于启动屏障和每轮完成屏障 |
| `shutdown` | 在 `worker_mutex` 下读写的生命周期退出状态 |
| 固定任务槽 | 预分配的 seed、目标位姿、bounds、模式和时间信息；本轮发布后只读 |
| 每工作线程异常槽 | 保存意外异常，确保完成计数不会因异常遗漏 |
| `mtx_` | 保留为结果缓存锁，与任务调度锁分开 |

任务槽的 seed 按 `model.nv` 预分配。位姿和 bounds 按值复制，不保存调用方对象的引用。每轮先写任务数据，再在同一把锁下递增序号并通知；工作线程通过带谓词的等待观察新序号，避免虚假唤醒、通知先于等待或上一轮通知迟到导致重复执行。

```text
构造：初始化模型和求解器 → 创建两个线程 → 等待两个线程就绪 → 返回

调用线程：填写任务 N → 唤醒两个线程 → 等待完成数为 2 → 整理并返回结果
Newton：  等待新序号 → 执行任务 N → 发布完成 → 等待下一任务
NLopt：   等待新序号 → 执行任务 N → 发布完成 → 等待下一任务

析构：设置退出状态 → 唤醒两个线程 → join 两个线程 → 释放求解器与同步对象
```

### 3.1 构造与启动失败

1. 完成模型、限位、求解器、任务槽及工作内存初始化后，再启动线程。
2. 两个线程分别登记就绪并进入任务等待循环；构造函数收到就绪计数为 2 后返回。这样第一轮不会承担线程尚未启动的延迟。
3. 如果第二个线程创建失败，构造函数必须设置退出状态、唤醒并回收已创建的第一个线程，再传播异常。构造失败不会调用完整对象的析构函数，不能依赖析构兜底。
4. 非实时启动阶段执行代表性预热，并在预热后清理本轮结果。就绪屏障只证明线程已启动，不能代替计算路径和内存页的预热。

### 3.2 每次调用流程

1. 按现有约定验证输入。单实例继续要求外部串行调用。
2. 记录本轮开始时间；确认上一轮两个线程都已完成，再清理结果和异常、重置两个求解器的取消状态。
3. 在调度锁下填写任务槽，设置完成数为 0，递增任务序号。
4. 释放锁，`work_cv.notify_all()`，调用线程在完成谓词上阻塞等待。
5. 两个线程分别领取同一序号任务，释放调度锁后运行各自求解器。求解过程中不持有调度锁。
6. 每个线程在所有结果写入、取消通知和求解器状态恢复完成后，登记一次完成。完成登记后不得再访问本轮任务和求解器状态，直到领取下一轮任务。
7. 调用线程观察到本轮完成数为 2 后，选择结果并返回。

两轮之间不重叠执行。即使一个线程尚未进入休眠，下一轮已经发布，它也会因任务序号变化立即领取任务，不需要依靠通知次数计数。

### 3.3 停止与结果可见性

`Speed` 成功、时间耗尽或工作线程异常时，通过原子取消标志通知另一求解器停止。工作线程需在进入底层求解、迭代和重启前检查取消；晚被调度的线程发现本轮已取消时，直接登记完成，不能自行清除取消状态。

所有取消标志只能在两个线程完成上一轮之后，由调用线程统一重置。所有结果写入发生在完成登记之前，由完成屏障建立返回端的可见性。调度锁和结果锁不嵌套持有，避免锁顺序依赖。

**不能仅因等待达到 1 ms 就直接返回并复用任务槽。** 此时未退出的工作线程可能继续写结果或使用旧参数。保持同步接口的第一版必须等待协作式退出；若将来要求调用方无论计算进度如何都在固定时刻返回，需要独立设计异步接口和结果版本隔离。

### 3.4 析构、配置变更和异常

外部调用约束继续为单实例串行使用：不得让析构、`setLimits()`、`SetSolveType()`、结果读取与正在执行的 `CartToJnt()` 并发。析构前由控制器停止提交并等待当前调用返回；内部退出协议不使“销毁仍被其他调用者使用的对象”成为合法操作。

`setLimits()` 在两线程空闲时校验并构造新的求解器，成功后整体替换，失败则保留原有可用配置。线程每次领取任务时访问当前求解器，不跨任务保存引用。必须将“初始化或重建求解器”和“启动线程”拆成两个内部函数，避免 `setLimits()` 再次创建线程。

线程入口设置异常边界：意外异常记录到本轮异常槽、取消另一求解器，并保证本线程完成登记。调用线程等待两个线程结束后再传播异常，避免 `std::terminate` 或永久等待。NLopt 的预期停止作为正常取消处理；现有 `catch (...) {}` 需要在 B 阶段细分，避免吞掉内存不足等意外错误。异常路径不作为实时性能承诺路径。

A 阶段同时将结果临界区的手工 `lock()` / `unlock()` 改为 RAII 锁。如果候选容器扩容或评分抛出异常，必须先释放结果锁；否则即使线程入口捕获异常，另一线程仍可能永久阻塞，完成屏障无法通过。

析构在退出标志发布后通知所有等待者，回收线程，再释放求解器及同步状态；线程创建和 `join()` 仅存在于启动、启动失败清理和析构路径。

## 4 1000 Hz 的时间预算

设实际允许的 IK 调用预算为 `B_ik`：

```text
1 ms ≥ 输入采集 + CartToJnt 墙钟耗时 + 控制律与通信 + 调度余量

CartToJnt 墙钟耗时
  = 参数准备 + 工作线程唤醒 + 并行求解及取消收尾的关键路径
    + 调用线程重新获调度 + 结果整理
```

因此 `maxtime` 不能直接等于整个伺服周期，更不能保留默认的 5 ms。举例：若其他控制工作及余量共需 300 μs，则 `B_ik = 700 μs`；若再为分发和收尾预留 150 μs，初始求解预算为 550 μs。**这只是预算示例，需用实际控制器测量值替换。** A 阶段保留库默认值以维持兼容，由控制器显式传入预算。

B 阶段建议将各层相对超时统一为从本轮入口计算的 `steady_clock` 绝对截止时间：

- 工作线程唤醒后先检查剩余时间；超时则直接完成，不开始新的求解。
- Newton 每轮开始、重计算前后和随机重启前检查截止时间与取消状态。
- NLopt 在每次 `optimize()` 前重新计算剩余预算，回调及有限差分逐维循环检查截止时间与取消状态。
- 剩余时间非正时不再调用 NLopt；不要向其传入 0 作为立即超时，NLopt 的非正时间上限表示禁用该停止条件。
- 记录“截止时间到达至两个线程都完成”的收尾延迟；降低外层 `maxtime` 本身不能消除这部分耗时。

NLopt 官方明确说明 `maxtime` 不是严格上界，并支持在目标或约束回调中通过 `force_stop()` 请求退出。因此跨线程只发布取消标志，`force_stop()` 由 NLopt 所属线程在回调内执行。[NLopt 停止条件与强制停止说明](https://nlopt.readthedocs.io/en/latest/NLopt_Reference/#stopping-criteria)

单次矩阵分解、库内部计算和线程重新调度仍可能越过截止时间。本方案提供可测量的延迟改善；是否满足控制器的期限要求，以第 8 节的整周期测试为准。

## 5 进一步提高计算效率

### 5.1 减少临时内存分配

优先复用以下工作区，按模型尺寸在构造或非实时配置阶段准备：

- 调度层的 seed、每工作线程的输出与重启 seed。
- Newton 的原生配置 `q`、`6 × nv` 雅可比、关节增量和临时向量；分解对象预设尺寸并复用，实际是否仍分配以检测为准。
- NLopt 的 `x`、差分扰动向量、原生配置、人工上下界和目标关节缓存。
- 增加写入已有缓冲区的配置转换内部接口，保留现有返回向量的公共便利函数。连续关节仍按 `(cos θ, sin θ)` 转换，外部输入输出仍为 `nv` 个标量。

`solutions.reserve()` 只保留外层容器容量，`clear()` 仍会销毁其中动态向量并释放各解的存储。若要复用，需要预分配解槽并以有效计数管理。`Speed` 在当前每个工作线程最多提交一个解的退出规则下可准备两个槽；其他模式的候选数随预算变化，不能未经接口约定就截断 `getSolutions()` 或返回数量。

先验证自有代码分配下降；不能据此宣称整个调用零分配。NLopt 内部工作区、第三方分解实现及调用方未预分配的 `q_out` 都需单独测量。预热也不能消除每次 `optimize()` 内可能发生的分配。

### 5.2 减少重复运动学计算

Newton 当前每轮分别为 FK 和雅可比转换同一组关节角。先将转换结果复用，并将只使用 tip 位姿的 `updateFramePlacements()` 评估为 `updateFramePlacement(tip_frame_id)`，减少无关 frame 更新。

随后对比“FK 加 `computeFrameJacobian()`”与“`computeJointJacobians()` 后更新目标 frame 并读取 `LOCAL` 雅可比”的实测成本。应核对实际链接的 Pinocchio 版本及数据前置条件；不能只删除前向计算。保持现有误差与 `LOCAL` 雅可比的坐标约定，并用数值差分和 FK 残差回归验证。模型分支多少、是否第一轮已收敛会影响收益，因此该项不预设加速倍数。

### 5.3 修复取消回调并优化 NLopt 梯度

当前 `cartSumSquaredError()` 在 `aborted` 或 `progress != -3` 时调用 `force_stop()` 后直接返回，未写入 `error[0]`；外层 `minfuncSumSquared()` 仍可能读取未初始化的 `result` 或 `v1`。并行抢先成功和取消都会触发这条路径。B 阶段应让误差回调所有出口返回确定值，并在停止或已成功时退出差分循环，不继续使用无效输出。其他误差回调一并检查。

梯度优化独立于线程改造：当前 SumSq 实现使用 `(f(x+h)-f(x))/(2h)`，分子为前向差分，分母却是中心差分的 `2h`，与标准前向差分不一致。先建立梯度数值检查，再以单独变更修正并比较收敛成功率、迭代数和耗时。

解析梯度作为后续候选：对现有 SE(3) 对数残差求导，需要考虑 `Jlog6`、坐标方向、符号及 bounds 的分段置零行为，不能直接以几何雅可比代替误差导数。仅在远离分段边界处先做数值差分一致性验证，再补充边界、接近 π 旋转和奇异位形用例。其主要预期收益是减少逐关节扰动引起的 FK 次数，具体收益由基准确认。

### 5.4 随机重启与结果锁

将三处 `rand()` 改为按实例、按工作线程独立的随机引擎，启动阶段播种，实时路径不调用熵源。提供测试可复现的固定种子方式；不同线程交错仍可能影响最终获胜结果，所以不能要求并行结果逐位相同。该变化会改变搜索序列，需比较成功率与解质量。

对于 `Manip*`，目前 `computeSingularValues()` 使用主对象共享的 `data`，移出结果锁前必须为每个工作线程提供独立评分工作区。之后在锁外计算评分，锁内只做去重和提交。`Speed` 路径优先保持简单；评分模式的锁优化不能被当作其主要收益。

最终 `std::sort()` 不是首要优化点，且 `getSolutions(..., errors)` 暴露排序信息。只求最小值或最大值会改变该接口行为，需要另行约定。

### 5.5 利用伺服轨迹连续性

控制器可将上一周期通过校验的解作为下一周期 seed，并根据实际关节跟随情况决定何时改用实测关节位置。配合 `Speed` 模式测量常规轨迹的迭代数。目标突变、不可达或上一轮失败时，沿用控制器已经定义的失败处理流程，不把错误返回时的 seed 当作成功解。

可选策略还包括只运行 Newton，或先给 Newton 一个短预算再唤醒 NLopt。这可能减少普通轨迹的唤醒开销，但也会推迟困难目标的第二算法搜索，改变双算法并行策略；不纳入 A、B 的默认实现，需用同一组轨迹单独比较。

## 6 控制器调度与集成

构造、配置、预热和析构放在非实时启动或停机阶段。控制循环只调用已准备好的实例，输入输出向量提前分配；日志和性能统计写入预分配缓冲区，在控制循环外汇总。

条件变量方案仍有线程唤醒和锁竞争。若 A、B 后调度延迟仍占主导，在目标 Linux 控制器测试 CPU 亲和性、实时调度优先级、内存锁定与预触页，并记录各配置的效果。这些策略由控制器显式配置，不由通用库静默修改整个进程。

两个工作线程均需得到及时调度。调用线程等待期间采用阻塞等待；高优先级线程在同一 CPU 上忙等可能让低优先级工作线程无法完成。若测试短时自旋或专用 CPU，必须一起评估优先级关系、CPU 占用和最坏延迟。标准互斥量也不能默认视为具有优先级继承；有需要时单独评估平台相关同步实现。

若整周期期限必须与求解耗时彻底解耦，后续可考虑异步预计算和带时间戳的最新有效解。该方案会改变结果新鲜度和控制时序，需要独立的接口与控制策略审阅。

## 8 验证与验收标准

### 8.1 功能与并发正确性

先保留并运行现有五种模式、连续关节、多圈 seed、链提取、限位和不可达目标测试，再增加：

1. 同一实例连续运行至少 100,000 次混合任务，交替成功、超时、非法输入、不同目标及 bounds，确保无旧结果串入、无死锁、无任务遗漏。
2. 控制测试调度，覆盖 Newton 先完成、NLopt 先完成、另一线程尚未领取任务即取消、虚假通知和下一轮立即提交；这些测试使用可控门闩或测试钩子，不依赖随机睡眠碰运气。
3. 每轮返回后验证两个线程均不再访问本轮状态；失败后再成功求解，确认取消和异常状态正确复位。
4. 空闲构造和析构、刚完成求解后析构、多实例并行使用，以及第二线程启动失败和工作线程意外异常的故障注入。
5. 空闲状态下更新限位、切换模式后继续求解；限位更新失败后原实例仍可使用，线程不重新创建。
6. 使用 ThreadSanitizer 检查自有同步代码，并用适用的地址和未定义行为检查验证生命周期。检测构建的耗时不作为性能结果。

不同并行执行时序可使候选数和最终解不同；回归检查 FK 精度、限位、连续关节语义和评分规则，不要求逐位复现旧结果。

### 8.2 线程生命周期验收

在独立测试进程中记录两个工作线程 ID 及创建、退出事件：成功构造只创建两个工作线程；连续调用过程中 ID 保持不变；无每周期创建或退出；析构后两个线程均被回收。启动失败时无残留线程。

Linux 可用 `strace -f -e trace=clone,clone3` 辅助检查系统线程创建，并结合线程 ID 和退出记录验证生命周期。跟踪运行仅用于结构验证，不使用带跟踪器的时延数据证明性能。外部库可能创建的线程要与本库两个工作线程分开归因。

### 8.3 性能测量

对基线、A、B 各版本使用相同机器人模型、目标轨迹、seed 策略、容差、模式、超时、Release 构建和硬件环境。为避免随机搜索改变比较样本，保存输入序列与随机种子，并重复实验；性能结果同时报告解的成功率。

测试集包含平滑轨迹、seed 已满足目标、目标突变、近奇异、接近限位、不可达、连续关节跨 ±π，以及系统后台负载。基线也使用同一预算，不能将 5 ms 预算的旧版与更短预算的新版直接比较为加速结果。

同时运行两类基准：紧密连续调用用于隔离库开销；按绝对时刻每 1 ms 释放任务的控制器循环用于测实际周期稳定性。后者记录迟到和漏周期，不通过事后跳过迟到样本掩盖超期。

| 指标 | 记录方式或意义 |
| --- | --- |
| `CartToJnt()` 总墙钟耗时 | p50、p95、p99、p99.9、最大观测值，包含等待和结果整理 |
| 任务发布至各线程开始计算 | 区分唤醒调度延迟与算法耗时 |
| 各求解器耗时、迭代与回调次数 | 定位计算热点与停止检查成本 |
| 取消发出至两线程都完成 | 衡量收尾尾部时延 |
| IK 超出 `B_ik` 的次数与比例 | 验证 IK 子预算 |
| 整周期超过 1 ms 的次数与比例 | 验证实际控制需求 |
| 成功率、FK 残差、限位、关节跳变 | 防止通过过早失败或降低精度换取耗时改善 |
| 分配次数、缺页和上下文切换 | 单独诊断运行，避免插桩扰动正式计时 |

### 8.4 通过条件

- **A 的结构验收：** 热路径中线程创建和回收次数为 0，生命周期和功能回归通过，无自有代码数据竞争或挂起。
- **性能改善验收：** 同条件下比较尾部时延和超期比例，成功率与精度不因缩短搜索或改算法而被隐性牺牲；达不到预期时使用分段计时决定下一项优化。
- **控制器验收：** 在事先确定的轨迹与负载范围内，预热后至少运行 1,000,000 个 1 kHz 周期，报告全部统计；目标为 IK 不超过已分配的 `B_ik` 且整周期零次超过 1 ms。若未达标，记录失败场景并继续优化，不能只凭平均耗时宣布通过。
- 零次观测超期属于该测试范围内的结果，不等于数学上的最坏执行时间保证；严格硬实时要求还需覆盖操作系统调度和依赖库执行上界。

控制器型号、CPU 核数、操作系统与实时内核配置、实际 URDF、当前调用参数、其他控制工作的耗时，是确定最终 `B_ik` 和复现环境所需的信息。A 的代码实施不依赖这些信息，但目标硬件的性能验收依赖它们。

## 9 审阅建议

建议先批准 A，完成线程生命周期改造及可复现基准；随后按 B 的顺序处理取消正确性、截止时间和内存及计算复用，每项保留独立对比结果。NLopt 梯度、随机序列、单求解器策略及异步接口分别评估，便于判断性能与解质量变化的来源。

本方案已完成阶段 A、B。后续 C、D 按测量结果继续评估，当前实现与验证范围以阶段 A、B 报告为准。
